# 渲染方案决策：要不要引进渲染引擎与前置库

> 状态：**推荐已给出，等你拍板。**
> 本文只回答"用什么画"，不回答"画成什么样"（后者见 `design.md` 与 `art/mockup.html`）。
> 相关：`architecture.md`（分层与插槽落点）

## 结论

**不引进。零运行期依赖，用原版绘制 + 自己的画法插槽。**

理由不是"自研更酷"，是三条可验证的事实：

### 1. 需求面太窄，框架的能力大部分用不上

要画的全部东西：一块可变宽的卡面（圆角/描边/半透明/渐变）、一个 16×16 物品图标
（交给原版 `renderItem`，附魔光效与耐久条白拿）、一行名字、一个数字，外加进场/合并/
退场的位移与缩放。同屏上限 5~6 张。

而候选前置提供的是：DOM 树、flex/grid 布局、事件冒泡、滚动容器、输入控件、焦点系统、
资源加载器、DevTools。**我们一件都不需要**——这个 mod 没有任何可交互控件，卡甚至不接受点击。

### 2. 纯客户端的卖点会被前置吃掉

README 的第一句话是"把 jar 丢进 `mods/` 即可，任何服务器、任何整合包都能用"。
加一个硬前置就变成"还要再装一个 mod，且它的版本得对得上"。对"拾取提示"这种
锦上添花的小组件，玩家不会为它去装第二个 mod。

### 3. 这条路我们走过两次，两次都是前置导致的死

| 版本 | 路线 | 死因 |
| --- | --- | --- |
| `D:\pickupnotice` | 自写 SDF shader + 用 Edge 把 CSS 烘成位图贴图 | **HTML 当贴图**：卡宽跟名字走，定宽贴图只能横拉，圆角/装饰全被重采样糊掉；且设计稿与实现两套真源 |
| `main @ v0.1.0` | ApricityUI 硬前置，HTML/CSS 卡面 | 玩家侧必须装 AUI；换画法等于重写渲染层 |
| `archive/selfdraw-v2` | 零依赖自绘 SDF | **死因不是技术**，是美术没定稿 + 手算坐标 + 没做真机验收（见下） |

第一条正是"HTML 当贴图是错误方向"——**卡宽可变**，任何"把设计稿烘成定宽 PNG"的路线
都会在非整倍 GUI scale 下露馅。这不是实现没做好，是方案本身与需求冲突。

## 候选对照

| 方案 | 1.20.1 Forge | 体积 | 许可 | 能提供 | 代价 |
| --- | --- | --- | --- | --- | --- |
| **不引进**（原版 `GuiGraphics` + 自写画法层） | — | 0 | — | 全部可控、分辨率无关、资源包可覆盖 | 圆角/模糊要自己实现 |
| ApricityUI | 有（snow 分支 `targets/forge-1.20.1`） | <1MB | LGPL-2.1/3.0 | 运行时 HTML/CSS 渲染全套 | 玩家侧硬前置；第三方维护节奏；v0.1.0 已试过并归档 |
| ModernUI-MC 3.12.0.1 | 有，但**1.20.1 已 EOL**（终版） | ~25MB（shadow 了框架 + Markflow） | LGPL-3 | 圆角/描边/四角渐变 shader、文字排版 | 硬前置；其"模糊"是全屏 backdrop，**没有区域模糊** |
| owo-lib | 有 | 中等 | MIT | 组件化 UI 框架 | 硬前置；我们要的是"画"不是"控件"，大部分能力用不上 |
| MCEF / 内嵌浏览器 | — | 巨大 | — | 真浏览器 | 与"丢进 mods 就能用"直接冲突，且卡宽问题依旧 |

两条补充事实（来自本机实测记录，不是猜的）：

- ModernUI 的圆角 shader 与上一版自写的 `gui_shape` **同名同格式**（`rendertype_round_rect`
  系，`POSITION_COLOR`），命名空间不同、无注册冲突——所以"要不要用它的算法"和
  "要不要依赖它"是**两件可以分开的事**。
- 1.20.1 是老化版本：ModernUI 在 1.20.1 线上已经停更。绑一个停更的引擎，
  长期等于把我们的 bug 修不了。

## 那"更美观/更现代"从哪来

不来自引擎。上一版 `archive/selfdraw-v2` 的引擎（SDF core shader，圆角/描边/圆/月牙
五种模式、解析抗锯齿）**技术上是对的**，它死后被打回的是**美术**。所以真正要解决的是
美术从哪里来、怎么快速迭代，而不是换渲染器。

三条可选（**这是下一步要讨论的**，本文不下结论）：

| 路线 | 卡面怎么来 | 优点 | 风险 |
| --- | --- | --- | --- |
| **A. 九宫格纹理** | 画一张 PNG，四角原样、中段平铺（loot-journal 就是这条） | 纹理不拉伸，不糊；能画得极精细；资源包天然可换 | 改设计要重画；分辨率相关 |
| **B. 程序化 SDF** | shader 现算圆角/描边/渐变，参数在 JSON | 分辨率无关；改参数即改外观；动画能做得更细（微光/扫光） | 参数调优慢；着色器调试成本高（见下方错题） |
| **C. 混合** | 静态装饰走九宫格纹理，动效强调走程序化 | 各取所长 | 两套东西要协调 |

## 这个决定怎么保持可逆

不管选 A/B/C，落点都是同一个接口：

```
CardStage（调度，不画一笔）
   └─ CardPainter（插槽）  ← 换画法只换这里
        ├─ BaselineCardPainter   骨架期的朴素占位实现
        ├─ 将来的 NineSlicePainter / SdfPainter / ...
```

`CardStage` 调用方只认 `CardPainter`。所以"要不要引进渲染引擎"这个问题，
从"选错了得重写"降级成"换一个实现类"——这才是本次骨架真正交付的东西。

## 上一版的两条死路（写下来，别重蹈）

1. **HTML 当贴图**：卡宽可变 × 定宽贴图 = 必然横拉。见上表。
2. **手算坐标 + 绝对/局部混用**：`archive/selfdraw-v2` 首帧"每张卡的装饰都在屏幕左边
   出现幽灵分身"，根因是一半用屏幕绝对坐标、一半用卡内局部坐标。
   骨架里的对策是**接口层就定死**：`CardSlot` 给屏幕坐标，painter 进卡后 `translate`
   一次，之后一律局部坐标。

另外两条与"编译过、单测绿"直接相关的教训：

- 渲染层**编译过 + 单测绿 = 零证据**。上一版就是这么宣布"构建成功"的，真机截图三个 bug。
  第一版 UI 必须让真机截图来验收。
- 1.20.1 core shader 的 JSON 里**每个 uniform 必须带 `values` 默认数组**，缺了在
  `ShaderInstance` 解析时直接崩 mod 加载（错误信息是 `Missing values, expected to find a JsonArray`）。
  上一版踩过。
